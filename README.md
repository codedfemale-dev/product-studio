# Product Studio by Coded Female

A guided, interactive example of a thoughtful product team setup. Learn why each part exists, follow the pre-filled Mentor Match example, then adapt the practices with your own team.

**[Open Product Studio](https://codedfemale-dev.github.io/product-studio/)** · **[Coded Female](https://codedfemale.com)**

## Learn through practice

Start here offers a seven-step journey, taking around 20 minutes at your own pace. Each step explains a principle, asks a practical decision question, gives feedback and opens the relevant workspace record. Exercises cover direction, evidence, acceptance criteria, Sprint planning, blockers, outcome review and an owned improvement experiment. Checks recognise specific edits and require an honest self-review. Each step includes three reflection statements and an optional written note. They do not assess actual team quality or certify learning. Earlier practice records remain readable; the updated guide asks for self-review before counting them as recorded steps.

A worked example connects discovery, the current outcome, P-102, shared quality, the outcome measure and the decision log. Team playbook explains information homes, example responsibilities, meeting purposes and the difference between acceptance criteria, Done and release readiness. A plain-language glossary is available throughout.

Learning notes can be viewed or downloaded, with takeaways and current practice examples. The guide can be collapsed or paused. Completed work has its own history view, and Undo can restore the last workspace change made in the current tab.

## Go a little deeper

Three optional activities support the guided journey:

- **Compare backlog examples:** inspect a vague request and a clearer starting point, reveal annotations and choose an observable criterion.
- **Change-request exercise:** ask why a request is urgent and explore three options. The frozen sample plan shows remaining item and point totals. These are illustrative estimates, not capacity or delivery forecasts. Exploring options never moves workspace cards. Explicitly saving reasoning adds or updates only the exercise's demo decision record and requires context, an explanation, an owner and a review trigger. Personal workspace records cannot be changed by this action.
- **Team handover:** use seven conversation prompts, then choose one change, a follow-up owner and a review point. The checklist and reflections appear in the downloaded learning notes. They do not assign work, send messages or create calendar events.

## Keep the reasoning connected

Priority suggestions show each item's current and suggested position, movement and the selected item's calculation. Backlog rows expose waiting prerequisites and checklist progress alongside the work.

Edited item, feedback and settings forms ask before discarding changes through Cancel, the close button or Escape. Navigating away or reloading also requests the browser's standard unfinished-edits warning when supported. This protects the open form; it does not create an automatic draft backup.

Existing meeting editors offer follow-up work and decision records. Save meeting notes first, create the follow-up, then save its title, owner and details. The saved records and meeting link to each other; cancelling creates neither a record nor a link. Deleting work or an essential cleans its meeting references, and Undo restores the complete workspace change.

Start here includes an optional four-part connected workflow exercise: evidence, priority reasoning, delivery quality and outcome review. Learners receive answer feedback, can explore the example boards and return, and record a short reflection. Progress and the reflection save with learning data and appear in downloaded learning notes. The exercise does not apply priorities or move cards automatically.

New records use readable references such as `P-112`, `O-4`, `E-12`, `M-17` and `F-4`. The next reference follows the existing sequence and saved counters. Existing identifiers and links are preserved; cancelling an unsaved new record allocates no reference. Counters are validated in imports and included in workspace backups.

An edited form displays **Unsaved form edits** both inside the editor and in the workspace status. After saving or discarding, the status returns to the actual workspace save state. Keyboard focus stays with usable controls after reordering, Sprint changes, filters and delivery moves. Closing an editor returns to its opener where available. Completed history omits reorder arrows. The overview includes selected work waiting on prerequisite items, and deletion confirmations explain affected links and ratings before the user decides.

## What is inside?

- **Overview:** Product Goal, Sprint Goal, current focus, flow counts, blockers and upcoming conversations.
- **Feedback inbox:** structured sources, observations, interpretations and uncertainty, with search, status filters and linked work. Create a follow-up item directly from a note.
- **Prioritisation lab:** adjustable impact and alignment weights, evidence confidence and relative effort. Scores suggest an order; applying it requires a named owner, rationale and explicit review, and records a decision.
- **Outcome roadmap:** editable Now, Next and Later outcomes, success measures, evidence, confidence and next learning steps.
- **Ordered backlog:** eleven connected examples with user needs, priorities, owners, optional estimates, acceptance criteria, dependencies and linked outcomes. Search, filter, reorder and add work to the Sprint.
- **Delivery board:** Ready, In progress, In review and Done. Drag cards or use accessible Move item controls. The example work-in-progress limit encourages finishing before starting. Linked prerequisites and editable checklists show outstanding work. Circular prerequisites are rejected, and unfinished prerequisites or checklist steps prevent recording Done. A human judgement of acceptance criteria and shared quality is still required.
- **Team calendar:** a navigable monthly calendar, a readable agenda list, meeting purposes, participants, agendas, notes and calendar export.
- **Team essentials:** discovery, metrics and guardrails, risks, decisions, roles, working agreements, Definition of Done and retrospective experiments.
- **Personalisation:** editable product details and Sprint dates, four backgrounds, local saving, JSON backup and restore, and reset with confirmation.

New work can start from a blank item, user story, bug report, research task or improvement experiment. Meeting templates cover planning, review, retrospective, refinement and discovery. Their prompts and agendas are editable.

Older backups remain compatible. Existing saved demos can explicitly add the new examples from Start here without replacing their existing values. Personal boards receive no automatic sample upgrade.

The calendar starts with a two-week example, including ten Daily Scrums, Sprint planning, Sprint review, Sprint retrospective, refinement and customer discovery. Sessions do not repeat automatically. Changing Sprint dates does not reschedule meetings.

All sample names, research and figures are illustrative. This is an educational example, not a claim about a real team. Meeting purposes were checked against the [Scrum Guide](https://scrumguides.org/scrum-guide.html); the team’s optional practices, estimates, priorities and meeting durations are examples to adapt. The roles include a Product Owner, Scrum Master and cross-functional Developers.

## Your personal copy

Changes are saved in **localStorage in your current browser**. The learning demo uses `codedfemale-product-studio-demo-v1`; My workspace retains the existing `codedfemale-product-studio-v1` key. Switching modes loads their independent records rather than copying one over the other. Learning progress uses `codedfemale-product-studio-learning-v1`; the last selected mode uses `codedfemale-product-studio-mode-v1`. Existing personal boards remain separate from the new guided practice. Each visitor gets their own independent workspace. There is no account, backend, shared editing, analytics, notification service or calendar connection. The hosting provider handles normal web requests; the application does not transmit board content.

Choose **Backup & restore → Export workspace** regularly. Clearing browser data, changing browsers, devices or website origins can make your saved work unavailable. To move to another device, export a backup and import it there. Import validates the file and asks before replacing the workspace in the current mode. Imports replace rather than merge. Export backs up that workspace, not lesson progress. Download learning notes separately. Reset affects only the current workspace and keeps the learning record; Undo is limited to one workspace change in the current tab and is cleared by switching modes or reloading. The initial local preview and GitHub Pages are different origins, so their saved work is separate.

Use one editing tab at a time. When the browser reports a differing saved workspace from another tab, this tab pauses saving, preserves its current state, offers export and lets you review the saved copy. Loading a reviewed copy rechecks that it has not changed and retains a one-step Undo in the current tab. This is protection against accidental overwrites, not collaborative editing or a transactional multi-user data store.

If storage fails, unsaved drafts remain available during mode switches in the current tab. They still need exporting before the tab closes or reloads. A persistent notice also warns when learning notes cannot save or have changed in another tab. An unreadable learning record is protected from automatic replacement; keep its raw recovery export before explicitly choosing a fresh record. Fresh learning progress leaves both team workspaces unchanged.

If an old saved workspace cannot be read, the app protects the original value and offers a raw recovery export. Storage failure leaves your changes in memory and shows a backup warning.

Calendar exports include all currently recorded meetings in the current workspace in `.ics` format using floating local times. Check time zones in the receiving calendar. Demo and personal event identifiers are separated. They are not invitations or a live subscription; participants are descriptive text. Importing the same export repeatedly may create duplicates depending on your calendar application.

## Run locally

No build step or installation is required. Serve the project directory with a static server, for example:

```sh
python3 -m http.server 8000
```

Open `http://localhost:8000`. Serving over HTTP gives consistent browser storage behaviour. Avoid opening the file directly with a `file:` URL.

Run the automated checks with Node.js:

```sh
node --test tests.cjs
```

## Publish on GitHub Pages

In the repository, open **Settings → Pages**. Choose **Deploy from a branch**, then **main** and **/ (root)**, and save. The app uses relative asset paths so it works at a project URL. No secrets or services are required. The `.nojekyll` marker disables Jekyll processing.

- `team-tools.js`: feedback, prioritisation, work and meeting templates, prerequisite links, checklists and additive demo examples.

No framework, external script, remote font request or AI service is used. User content is escaped before HTML rendering. The app limits imports to 5 MB and 1,000 records per collection. This is a personal showcase and planning tool; shared team use would require a separate persistence and access design.

## Review with someone new

Start here → Optional tools and practice → Review the demo’s usability offers four tasks: find evidence, explain and change priority, create a meeting follow-up, and save/recover an edit with Undo. Each task opens the learning demo and offers a return banner. Record Clear, Hesitated or Could not complete, plus observations. Notes save with learning data, can be downloaded separately and are included in learning notes. No feedback is sent. Finishing hides the banner and retains notes; a fresh learning record clears them. Download a review before reusing the fields for another person.
